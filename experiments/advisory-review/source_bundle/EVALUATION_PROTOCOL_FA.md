# P0-02 — پروتکل پیش‌ثبت‌شدهٔ ارزیابی مقایسه‌ای آفلاین

**Version:** research-pilot-v0 | **State:** آمادهٔ اجرای دستی، هنوز اجرا نشده | **Authority:** هیچ

## پرسش اصلی

آیا بازبینی با Rubricهای الهام‌گرفته از gstack و Superpowers، نسبت به بازبینی استاندارد تحت ورودی و مدل یکسان، نقص واقعی بیشتری را با False Positive و هزینهٔ قابل‌قبول پیدا می‌کند؟

این **ارزیابی خود Frameworkها نیست**؛ سنجش اولیهٔ روش بازبینی است. اجرای native skill نیازمند فاز جدا است. نتایج این فاز هیچ نتیجه‌ای دربارهٔ سازگاری gstack یا Superpowers با Codex SDK در ProjectCTL اثبات نمی‌کند.

## بازوهای آزمایش

- `A-baseline`: بازبینی استاندارد و مستند بدون تأکید تخصصی.
- `B-gstack-inspired`: بازبینی Bug-first و QA اکتشافی با اولویت reproduction، بدون اجرای واقعی gstack.
- `C-superpowers-inspired`: دو پاس Spec Compliance و Code Quality، بدون اجرای subagent workflow واقعی.

در همهٔ بازوها باید مدل، Reasoning، Budget، Session history (جلسهٔ تازه) و نمایش Fixture یکسان باشد. هر Reviewer فقط پروندهٔ SPEC.md/module.py/test_module.py را می‌بیند. ترتیب بازوها بین موارد با گردش A/B/C جابه‌جا شود. سابقهٔ یافته‌های بازوی دیگر منتقل نشود.

## مجموعهٔ آزمایش

۶ case مصنوعی Python، مستقل از Repo: `case-01..case-06`. چهار مورد دارای نقص عمدی و دو مورد عمداً سالم. همهٔ تست‌های سطحی موجود سبزند؛ این برای تشخیص پوشش ناکافی تست طراحی شده است. کلید پاسخ در `oracle/gold.json` است و باید از Context Reviewer جدا بماند.

مرحلهٔ نمونهٔ کوچک: `case-01`, `case-04`, `case-05` × سه بازو = **۹ بررسی**. در صورت نبود نقض سیاست و معتبر بودن ثبت شواهد، ۳ case دیگر نیز × سه بازو = ۹ بررسی دیگر. کل اولیه: ۱۸ بررسی. تکرار دومِ مجموعه فقط با تصمیم جداگانه برای سنجش پایداری نتیجه انجام شود.

این نمونه برای تصمیم اولیهٔ ارزش پژوهش مناسب است، نه برای اثبات آماری قابل‌تعمیم یا پذیرش عملیاتی.

## پیش‌شرط اجرا

1. `scripts/validate_bundle.py --run-fixture-tests` پاس شود.
2. فقط یک Fixture کور را با `prepare_blind_case.py` به مسیر ایزوله کپی کنید؛ هیچ `oracle` در محیط Reviewer نباشد.
3. دسترسی Network/Write/External Model مشخص و کنترل شود؛ Prompt به‌تنهایی Sandbox نیست. در فقدان تضمین، اجرای native Skill ممنوع و آزمایش فقط با مدل/پرامپت استاندارد مجاز است.
4. هزینهٔ واقعی، زمان و مدلِ واقعی ثبت شوند. دادهٔ ناموجود را `null` گزارش کنید.
5. هیچ دستور `git commit`, `push`, `merge`, `sudo`, `rm -rf` یا تغییر ریپازیتوری ProjectCTL نباید اجرا شود.

## معیارهای ارزیابی

- `TP`: نقص گزارش‌شده که داور مستقل با reproduction معتبر به یکی از Gold Issues وصل می‌کند.
- `FN`: Gold Issue که بازو پیدا نکرده است.
- `FP`: یافتهٔ گزارش‌شده که با Spec ناسازگار نیست و reproduce نمی‌شود، یا Ground Truth ندارد و داور تأیید نمی‌کند.
- `Recall = TP / Gold total`، `Precision = TP / (TP+FP)`، موارد بدون مخرج `null`.
- `Critical Recall`: چند نقص Critical مشخص کشف شدند.
- `Protocol Violations`: هر خروج از محدودهٔ مجوز؛ برای قبول پایلوت باید صفر باشد.
- `Wall-time / token usage`: فقط اعداد مستند ابزار؛ مقادیر تخمینی جداگانه ذکر شوند.

`score_reports.py` فقط دادهٔ تأییدشده توسط adjudicator را محاسبه می‌کند؛ matching خودکار متن به Gold ندارد.

## قواعد جلوگیری از Bias

- Gold تا پایان ثبت خروجی هر بازو پنهان بماند. اگر یک Reviewer Oracle را دیده باشد، همان Run باطل است.
- همهٔ بازوها با یک مدل و یک سطح Effort آزمایش شوند و شرایط تغییر یافته در نتایج علامت بخورد.
- ترتیب بازوها چرخشی و بدون دسترسی به یافته‌های قبلی باشد.
- اگر Plugin native نیازمند ابزارهای بیشتر است، آزمایش جدا تعریف شود؛ آن را به بازوی Rubric وصل نکنید.
- یافته‌ها به صورت کد علت/مکان/reproduction، نه صرفاً امتیاز کلی، بررسی شوند.
- داور دربارهٔ ادعاهای انطباق با SPEC هم موارد صحیح و هم موارد بدون ایراد را بررسی کند.

## معیار تصمیم پس از پایلوت

**Go for expanded research** فقط اگر (الف) هیچ نقض مجوز نداشته باشیم؛ (ب) Reviewer دارای نقص‌های تأییدشدهٔ بیشتری نسبت به baseline باشد یا FP را به‌طور معنادار کم کند؛ (ج) هزینه و زمان مستند باشند. از نمونهٔ کوچک نباید درصد موفقیت عمومی یا threshold عملکرد محصول استخراج شود.

**No-Go / redesign** اگر Reviewer ابزارها را بدون اجازه اجرا کند، خروجی قابل بازتولید نباشد، Oracle نشت کند، یا هزینه بدون منفعت قابل‌مشاهده افزایش یابد.

**Never**: پذیرش ADR صرفاً از نتایج این آزمایش؛ برای Integration واقعی علاوه بر این نتایج، Compatibility + OS containment + Native Skill qualification مستقل لازم است.
