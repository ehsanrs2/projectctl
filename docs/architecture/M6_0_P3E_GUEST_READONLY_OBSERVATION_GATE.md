# M6.0 P3e — Disposable Debian guest read-only observation gate

**Baseline:** merged P3d PR #111, `main@c495c22b0bd5a19ec57b7759340ca85ea71aa012`.

**Status:** NONPRIVILEGED GUEST OBSERVATION TOOL ONLY. No selected or attested disposable VM, no independent administrator/observer, no genuine two-principal denial, no dedicated custody filesystem, no host rollback protection, no approved privileged experiment.

**Decision:** `P3E_NO_GO_SEPARATE_VM_UNATTESTED`.

## 1. Why this phase differs from P3d

P3d validates the *shape of a proposed human authorization dossier*, without seeing an OS. P3e provides a very small, opt-in **read-only observation of a running environment that the human operator has already independently determined to be a separate throwaway Debian guest**. It does **not** establish that the environment actually is isolated, private, disposable, or controlled by a distinct administrator. The main development Debian checkout must not automatically be treated as the disposable target.

The reason for this boundary is practical: the actual VM, hypervisor, storage backing and independent administrator have **not been identified**. No PR or checker can truthfully choose them. The next real step must be selection by the human owner before any guest-side observation is represented as a trial input.

## 2. Proposed owner-managed handoff

**Step A — separate host/guest choice, outside the repo and before running the guest command.** The owner names an *actual new disposable guest* under a known VM host/hypervisor (QEMU/KVM, VirtualBox or another explicitly documented provider), verifies that it does not contain real ProjectCTL databases/WAL/keys or the user's live working state, and identifies the individual with exclusive root/hypervisor administration. No disk provisioning, account creation, service, password, mount change or VM creation is authorized by this document. If no such existing or separately owner-approved guest is available, **STOP HERE**.

**Step B — independent human boundary review.** Confirm that the untrusted ProjectCTL writer does not share control of the hypervisor, root/sudo credential, guest service manager, admin-owned code and ancestor paths, or snapshot/disk rollback channel. A separate administrator and a distinct independent observer must be named and their permissions privately reviewed. Guest kernel and host/hypervisor remain in the TCB; local DAC does not defend against hostile host disk rollback. With root/snapshot rollback in attacker scope, P3-C2/T1 requires a separately approved external monotonic anchor, not a local filesystem claim.

**Step C — limited guest metadata observation, only after A and B.** Review the Python source. Run as a **normal user inside that specific throwaway guest only**:

```bash
python scripts/p3e_guest_readonly_probe.py --i-am-on-a-separate-disposable-vm
```

The explicit flag is a **self-assertion, not proof**. Without it, the script refuses before inspecting anything. It also refuses root/setuid/setgid invocation. The tool reads only fixed bounded sources: `/etc/debian_version` (256 B), `/sys/class/dmi/id/sys_vendor` (256 B), `/sys/class/dmi/id/product_name` (256 B), and `/proc/self/status` (32 KiB). It reads no caller-supplied path and opens no project DB, WAL, or source checkout files. No subprocess, network connection, file creation, service invocation or privileged system mutation.

**Output is only fixed enums.** It cannot contain the DMI product, kernel release, host/user/machine ID, hostname, UID/GID, raw mount, storage path, source contents or process status. DMI brand matching (e.g. QEMU/VirtualBox/VMware) is a weak spoofable **virtualization hint**, not proof of a guest rather than a container, independent administrative control, actual storage backing or the durability of a future ledger. Effective capabilities are those of this observing process only, not the legacy v2 writer or proposed Custodian.

**Step D — separately controlled private evidence.** The *actual* hypervisor guest ID, trusted administrator identity, host and guest snapshot/rollback assumptions, dedicated nonvolatile disk provenance, and approved custody path must be reviewed by the owner and a separate security observer in a limited-access record **outside the public repository**. Do not commit sensitive inventory, secrets, administrator contact details, hypervisor configuration, real user IDs or privileged command lists. Redacted enum-only P3e output may be reviewed without claiming it is attested. No independent witness is generated by this script.

**Step E — later, only on a concrete approved disposable target.** A new separately scoped document and human authorization must name the precise guest, admin, independent observer, persistent target FS/path and exact commands for any identity/service/storage/fault injection. P3a can later observe an **existing** candidate path as an ordinary user, but P3a/P3b results remain NO-GO. Never use the observed `/tmp` rw tmpfs as durable custody storage. Do not run the 28 P3-F tests or touch real project state merely because P3e printed JSON.

## 3. Meaning of the output

| Item | Interpretation |
| --- | --- |
| `operator_disposable_vm_assertion=UNVERIFIED_SELF_ASSERTION` | Caller accepted the flag, but guest existence and owner intent were not authenticated |
| `virtualization_hint=DMI_VIRTUAL_BRAND_HINT_ONLY` | Raw self-observed DMI has a recognized substring; also possible in nested containers or spoofed sysfs |
| `virtualization_hint=DMI_NO_RECOGNIZED_VIRTUAL_BRAND` / `DMI_NOT_READABLE` | No recognized data; **not** proof of bare metal |
| `effective_capability_observation=CAPABILITIES_ZERO_OBSERVED` | Only the **current probe process** reported zero CapEff; no writer/custodian policy proven |
| `decision=P3E_NO_GO_SEPARATE_VM_UNATTESTED` | The sole allowable security disposition |
| `actual_p3_cases_executed=0` | None of P3-F01–F28 has been executed |

No output ever says `GO`. A successful exit proves only that bounded observation ran for an opt-in unprivileged caller. It does not imply CRED/BLOB/SEQ/DUR/AUTH/EXP, authenticated source epoch P0/P1, producer P2, Custodian P3 or consumer P4.
